# Nightingale 前端设计审查与后续优化计划

日期：2026-09-05  
性质：现有产品的设计审查与实施提案；本次未修改产品代码。  
依据：当前工作区源码、现行产品约束、四种角色的实际页面。旧 C2 任务卡仅用于理解背景，不作为当前功能清单。

## 1. 结论

建议沿用当前的暖白背景、深青色导航和少量衬线标题，做一次系统性的精修。现有界面已有合适的医疗产品气质，也有完整的业务结构。继续换主题，收益小于整理信息层级、阅读空间和控件规则。

目前影响精致程度的主要原因是：

1. **功能已完整，页面之间的完成度不一致。** 工作收件箱、患者首页和管理员总览已有统一气质；检查结果、通知、导入和部分设置表单仍有默认浏览器控件或另一套间距。
2. **主要内容没有获得足够的注意力和空间。** 空置的右侧工具栏持续占位，顶部说明与重复元信息较多，临床正文及关键操作反而变小。
3. **按钮、标签和说明的主次不稳定。** 患者 Check-in 的多个不同操作都显示为实心绿色；有的技术说明比真正需要完成的任务更醒目。
4. **字体、图标和文字处理缺少统一规则。** 字号过碎、日期格式混用、摘要截断到半个单词、符号图标风格混杂。这些小问题累积成“拼接感”。
5. **样式多轮叠加，容易出现局部修好、别处变差。** 后续需要逐步收敛规则，而不是继续在全局样式末尾追加覆盖。

“更加美观”在这里应体现为：打开页面时更容易看见重点，阅读时更安静，操作时更明确，各个角色的界面像同一个产品。

## 2. 审查范围与证据边界

### 2.1 方法

- 扫描当前全部 41 个 TSX 文件，包括页面、共享组件和遗留组件；初次扫描约 7,233 行。检查路由、界面文案、控件、状态分支、样式和字体声明。
- 检查 `index.css` 与后加载的 `workspace.css`，结合实际浏览器界面判断覆盖关系。
- 使用当前前端源码，在独立的合成数据环境中登录 clinician、staff、patient、admin。没有重置现有业务数据库。
- 主要检查桌面 1440 × 1000；补查临床界面 1280 × 800，以及患者页面、来源面板 390 × 844。并非每一页都完成了全部尺寸组合。
- 为观察已有检查结果和通知模块，在独立审查环境启用对应开关；未改动现有运行环境的功能配置。

### 2.2 覆盖清单

| 区域 | 实际检查 | 覆盖限制 |
|---|---|---|
| 认证 | 登录、错误凭据、注册无效邀请、初始化无效令牌 | 有效邀请提交、过期/已用令牌等状态仅查源码 |
| 医生/护理工作区 | 患者目录、Glance、Timeline、Notes、Event 阅读、来源、任务、工作收件箱 | 未提交正式临床修改 |
| 协作与修订 | 评论空状态、版本入口及显示、审计信息；编辑与冲突界面源码 | 未制造并发冲突、执行回滚或完整评论线程交互 |
| 新问诊 | 手工输入页面、合成示例、转写复核预览、确认项 | 未创建新问诊；语音只观察禁用状态并检查其他状态源码 |
| 检查结果 | 禁用/启用后的空列表、开单表单及完整流程界面源码 | 未上传报告、提交医生复核或发送患者说明 |
| Copilot / Coverage | Copilot 空状态、Coverage 列表、Shadow Learning 页面 | 未发送 AI 请求；答案与引用状态仅查源码 |
| 患者 | Today、Care Plan、Check-in 初始及进行中、Visit Summaries、说明阅读、移动端 | 未发送症状消息、完成任务或提交确认；安全触发状态仅查源码 |
| 管理员 | 总览、邀请、导入、审计、设置、提醒策略、Shadow Learning | 未创建账户、导入数据或保存策略 |
| 通知 | 启用后的通知弹层和真实合成通知列表 | 未执行标记已读及完整跳转链路 |

因此，本报告是完整的源码与页面设计覆盖，不代表所有业务状态已完成交互验收，也不代表临床可用性、无障碍或性能已经达标。

当前工作区存在大量已有未提交修改和新增文件，审查期间也观察到检查结果、通知等模块继续更新。交付前已复查相关源码，主要设计问题仍存在；文件统计与浏览器观察应理解为本次审查的时间截面。执行任何一批优化前应重新确认当前基线，避免覆盖其他工作的结果。旧 `PatientPage / PatientHeader / Timeline / EventCard / IngestPanel` 属于源码审查范围；当前入口使用新的角色工作区，不应把旧页面误认为现行主界面或直接删除。

## 3. 应当保留的设计基础

- 暖白底色与青绿色：已经能够兼顾专业感和亲近感。
- 医生与护理人员共用工作区、患者独立界面、管理员独立工作区的关系。
- Glance、Timeline、Notes、Tasks、Tests 的业务分工，以及已存在的工作收件箱、私人草稿、通知、Copilot 和语音入口。
- 来源高亮、原始记录与 AI/人工内容区分、任务状态、说明阅读与确认的区别。
- 目前较好的工作收件箱行布局和管理员总览，可作为同一产品内部的参考。

不建议新增装饰性指标、虚构病人数据、额外仪表盘或与工作无关的插画来填补空白。信息少的页面可以安静；需要调整的是空白与真实内容之间的比例。

## 4. 全局设计规则建议

以下为建议规格，需通过真实页面样张验证，并非声称目前已实施。

| 项目 | 建议规则 | 目的 |
|---|---|---|
| 字体 | 功能界面以一套无衬线字体为主；衬线仅用于患者姓名、欢迎语等少量身份性标题 | 保留气质，减少工作页面的视觉跳变 |
| 字体资源 | 当前声明 Inter，但未发现配套字体加载资源。明确使用系统字体，或提供经许可、可稳定加载的字体资源 | 避免不同设备呈现不可控差异 |
| 字号 | 临床正文约 14–16px，患者正文约 16px，辅助信息约 12–13px；常用标题约 24–28px | 不靠 9–11px 临床信息换取密度 |
| 字重 | 用少量常规/中等/强调字重；大段正文不加粗 | 标题、事实、说明具有稳定层级 |
| 颜色 | 统一背景、表面、边框、正文、次要文字、品牌色与状态色；状态同时有文字 | 降低颜色噪声，避免仅凭颜色表达风险 |
| 间距 | 优先收敛到 4、8、12、16、24、32px 的节奏 | 减少“这里松、那里挤” |
| 容器 | 页面和普通列表以留白、分隔线组织；卡片用于独立任务或内容组；浮层才使用明显阴影 | 减少卡片套卡片 |
| 按钮 | 一个局部任务区域只有一个主要操作；其余分为普通、文字和危险操作；明确禁用与进行中 | 用户能立即找到下一步 |
| 图标 | 一套统一尺寸、笔画的图标，常用 16/20px；图标按钮有可访问名称 | 替换混杂 Unicode 符号，减少装饰性噪声 |
| 日期 | 统一日期、时间、时区和相对时间的表达；区分事件发生时间与记录修改时间 | 保持纵向病历含义准确 |
| 空状态 | 区分“没有数据”“功能未启用”“加载中”“权限不可用”“出错”；提供实际可用的下一步 | 不把不同状态都做成巨大空卡片 |

样式扫描中，`index.css` 约 1,905 行、1,494 条规则、314 种不同的字面十六进制颜色；`workspace.css` 约 256 行、239 条规则。**这些包括历史覆盖和响应式规则，不代表一页显示了 314 种颜色，也不等于每条重复规则都是错误。** 但它说明继续分散增加颜色与控件规则会提高维护成本。

建议按正在调整的页面提取已经重复的 Button、Field、Status、Metadata、EmptyState 规则。不预先建立庞大组件库，也不一次性重写全部 CSS。

## 5. 逐区域发现与优化方向

### 5.1 临床工作区与 Glance：最高优先级

**观察到的问题**

- 在 1440px 宽的桌面，左栏约 232px，右栏约 380px。右侧默认打开的空 Copilot 占据约四分之一屏幕；护理角色也有空工具空间。
- 中央区域同时包含患者头、标签导航、页面标题、解释、数量，以及逐条重复的状态、原因、日期、来源和操作。五条重点需要继续滚动；当前画面约能完整看到三条及下一条的一部分。
- 当前视觉密度受整个视口宽度影响，与中央实际可用宽度未完全对应。

**建议**

- 保留三栏能力；没有选中来源或使用工具时，默认收起右栏，让病历获得阅读空间。打开来源或 Copilot 后再展示上下文面板。这是首批样张要验证的交互提案。
- 将患者身份头与次要信息压缩为稳定的两层；把重复说明移至简短副标题或帮助位置。
- 每条重点稳定呈现“事实 → 当前状态/重要原因 → 来源/操作”。合并元信息行，降低重复按钮边框，避免把所有操作做成同等强度。
- 保留原因和可追溯入口；不得为了首屏数量改写临床含义或隐藏关键否定信息。
- 首批用同一组合成病历对比来源关闭/打开两种状态。目标是在 1440 × 900 的标准示例中，无需滚动即可看见五项核心标题、状态和来源入口；详细解释允许展开。长文本不能靠无限缩字号满足目标。

“十秒理解当前状态”需要真实阅读任务验证；本次仅确认空间与层级问题，没有完成计时用户测试。

### 5.2 来源面板：证据应该先于结构说明

当前精确引文高亮可以工作，这是必须保留的优势。但面板中存在重复的 Review context、展开的 Event → Artifact → Span 链、重复来源说明；窄屏还有两个含义相近的关闭按钮。

建议顺序为：**事件/作者/日期 → 精确引文 → 上下文原文 → 来源详情**。完整链路放入可展开的详情；原始、AI、医生或护理作者身份保持可见。统一一个顶层关闭动作，内部返回单独命名。验证键盘焦点、关闭返回点和患者切换清理。

这只调整展示顺序，不减少精确定位、版本过期提示或来源权限校验。

### 5.3 Timeline、Event、Notes：从卡片堆叠转为病历阅读

| 当前观察 | 建议 |
|---|---|
| Timeline 同一事件重复日期、通用类型与大卡片，但缺少可快速辨别的内容 | 建立日期层级与更紧凑的事件行；如采用预览，只使用已授权内容的有边界原文，不生成新判断 |
| 打开 Event 后新增顶层标签，原导航位置移动 | 保持主导航稳定，在内容区表达事件路径与返回来源 |
| Event 标题、文档选择、阅读器标题、记录时间和技术说明层层重复 | 使用清晰的文档阅读器；元信息集中一行，辅助说明折叠 |
| Order examination 位于阅读器中，样式接近原生链接/按钮 | 将现有动作按记录、跟进、讨论组织在一致的工具区域 |
| Notes 嵌套容器、文字偏小，预览会截断到半个单词 | 扁平列表，提升预览字号，显示省略号与完整阅读入口 |
| 版本入口、日期和比较控件很小；日期格式与其他页面不同 | 统一版本工具栏与时间格式，提高 diff 和版本信息可读性 |

Notes 的具体截断来自 `ClinicalNotesView.tsx` 中字符串拼接后 `.slice(0, 220)`；实际出现 `Bloo`、`Schedu` 之类结尾。需要边界合理的视觉截断，不应用新的 AI 摘要替代原文。

Timeline 继续按真实 Event 和显式 encounter 分组；评论、修订仍留在事件内部。私人草稿、已保存版本和正式记录必须有明确状态，不能借设计调整暗中变成自动发布。

### 5.4 Tasks、工作收件箱、Tests、通知：统一“待处理事项”的语言

- **Tasks：** 常驻的长篇权限/状态说明抢占顶部，空分组占用空间。优先展示任务、状态、负责人、到期时间；解释靠近相关动作，空分组收紧，完成项继续可折叠。
- **工作收件箱：** 现有行式布局适合作为参考。统一其状态、时间和任务页的表达。少量数据造成的留白并非必须补满的缺陷。
- **Tests：** 导航叫 Tests、页名叫 Examinations；默认字号、内边距、输入框与其他页不同。五个流程阶段空分组加详情区，再叠加全局右栏，形成过多竞争区域。建议统一名称，使用紧凑的阶段导航、列表和阅读区；无选中项时合理释放详情空间。
- **开单表单：** 按语义分组，控制表单宽度；合理配对字段，避免多个横跨整页的输入。事件选项中的原始 ISO 时间改为统一可读格式。
- **通知：** 当前弹层有默认灰色按钮、蓝色下划线链接，以及 `initial/overdue/escalation` 等原始状态。应改成可读标签、统一操作与明确关闭方式，布局与锚点匹配。只能展示接口已授权返回的信息，不能从 URL 推断患者资料。

保留完整的“开单 → 报告 → 医生复核 → 患者沟通”关系。结果处理、患者沟通与后续任务完成是不同状态，不能统一成一个含混的“完成”。

### 5.5 新问诊与语音：把输入和复核提前

在 1440 × 1000 的实际页面中，禁用的语音区域、标题说明、权限卡片、步骤说明和元信息位于输入前，手工输入框接近页面约 850px 处才开始。

建议让可用的输入方式与输入框尽早出现；语音不可用时显示简短状态和可展开说明。复核阶段再显示原文与规范化片段的对照；字符范围、内部索引等技术细节按需展开。

医生/患者说话人、药物剂量和混合语言的三项明确复核应放在最终确认附近，继续要求用户主动确认。保留阻断错误和原始转写不可覆盖的规则。不新增录音或自动转写能力。

### 5.6 患者端：下一步比装饰更重要

- **Today：** 现有温和气质合适，但深色 Check-in 卡片比真实下一步更醒目。降低次要入口的视觉重量，优先突出实际 care action；减少主任务区无意义的高度。
- **Care Plan：** 四个相同的大分组把零条目也展开，实际待处理内容不够靠前。按已有状态组织：当前行动优先、待核实明确、完成项折叠、空组简化。
- **Check-in：** 进行中页面的回答、补充、纠正、跳过、结束、放弃等操作都呈现实心绿色。这不只是偏好问题：后面的 `.patient-checkin-composer button` 通用规则覆盖了部分既有意图按钮样式。应明确选中模式、主要发送、次要结束和危险放弃，不合并不同状态机动作。
- **患者说明与 Visit Summaries：** 多张卡片只有通用标题、日期和按钮。可展示已有患者授权投影里的简短原文预览；不得读取内部临床记录来补内容，也不改变“查看”和“确认已读”的语义。
- **阅读返回：** 实际观察到选中的说明在切换 Today 后继续存在并把视线带到下方。建议读者状态与页面路径关系更明确，提供可预期的返回与关闭。
- **手机：** 390px 下已能正常排列且所查页面没有横向溢出。继续优化两行导航的高度、辅助字号和点击区域；复杂临床资料不应简单按桌面同比缩小。

保留必要的安全指导。减少重复提醒时，不得隐藏危险症状触发后的明确指引，也不得暗示系统已经通知诊所。

### 5.7 管理端与认证：完成同一套产品的最后一圈

| 页面 | 主要问题 | 优化方向 |
|---|---|---|
| 总览 | 相对成熟，可作为内部参考 | 保留表格结构，统一状态与时间 |
| 邀请 | 更接近独立登录卡片，圆角阴影和全宽按钮与总览不同 | 使用一致的后台表单，合理限制宽度 |
| 导入 | Source system 接近原生矮输入，文件选择器未统一 | 统一字段与上传区域，保留格式说明及导入前预览 |
| 提醒设置 | 字段间距、标题、统计块与其他设置不一致 | 统一两列/单列表单规则、保存反馈和禁用提示 |
| 设置 | 三项选择在两列内形成孤立一项，说明冗长 | 按实际宽度三列或单列；简明摘要加技术详情 |
| Shadow Learning | 重复标题、较大的元信息卡片、技术标识占前景 | 区分当前策略、离线证据、受控操作；保留不理想指标和限制 |
| 登录/注册/初始化 | 实现说明如 session、invite-bound、deployment-authorised 很突出 | 用用户能理解的访问目的作为主文案；必要的管理技术信息放次级位置 |

管理员需要部分技术信息，因此不应一律移除。调整的是信息顺序。邀请绑定角色、账户权限和服务端约束继续生效。

## 6. 建议实施批次

### A. 真实页面样张与共同规则

**内容：** 重新确认当前基线；使用同一份真实合成病历，制作 Glance 来源关闭/打开两种状态；补一组字体、按钮、标签、输入框、空状态及移动端来源样张。

**产出：** 可点击的真实页面设计样张和一页简明规格。用户能够直接比较改前改后，而不需要判断抽象术语。

**完成条件：** 确认字体气质、信息密度、右栏默认行为和操作层级；保留来源、作者与临床语义。先评审这一小组，再向其他页面推广。

### B. 共同控件与临床主阅读路径
